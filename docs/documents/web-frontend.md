# Web frontend

The Next.js app behind the website, in `app/frontend/`. It is built with the App Router, TypeScript, Tailwind CSS v4 and bun. The website's plan is in `.scratch/website/spec.md`; the API it talks to is in [web-backend.md](web-backend.md).

## The API proxy

`next.config.ts` rewrites `/api/:path*` to `${BACKEND_URL}/api/:path*`, so the browser only talks to Next and no CORS is needed. `BACKEND_URL` is read when the server starts and defaults to `http://127.0.0.1:8000`; set it to point at another backend (`BACKEND_URL=http://backend:8000 just frontend`). Try it: `curl 'http://localhost:3000/api/feedback?guess=crane&answer=speed'`.

## Themes

The gpui app's ten palettes (see [gpui-app.md](gpui-app.md)) with the same role names. `themes.css` has one `[data-theme="<id>"]` block per theme, with these variables:

- plain roles: `--background`, `--surface`, `--overlay`, `--highlight-low`, `--highlight-med`, `--highlight-high`, `--text`, `--subtle`, `--muted`, `--heading`, `--error`, `--success`, `--accent`,
- Paint roles, a fill and the colour of the letter on it: `--correct`, `--present`, `--absent`, `--absent-key`, each with `--on-correct`, `--on-present`, `--on-absent`, `--on-absent-key`.

`tokens.css` maps each to a Tailwind colour of the same name (`@theme inline`), so components write `bg-surface`, `text-subtle`, `border-highlight-med`, or a tile as `bg-correct text-on-correct`. Components never use fixed colours, so every theme works everywhere. When a gpui palette changes, update `themes.css` and `themes.ts` to match.

**Default and choice.** There is no "follow the system" option and `prefers-color-scheme` does not choose the theme. With nothing saved the theme is Rosé Pine Dawn (id `rose-pine-dawn`, the light Rosé Pine; `DEFAULT_THEME` in `lib/theme/theme-script.ts`). Picking a theme saves its id in `localStorage` (`wordle-theme`). A saved value that is not a theme id, such as the `system` that older visits stored, is ignored and gives Rosé Pine Dawn.

**No flash.** `layout.tsx` puts an inline script (`lib/theme/theme-script.ts`) in `<head>`. It runs before the first paint: it reads `localStorage` (inside `try/catch`, since storage can be blocked), falls back to `DEFAULT_THEME` for a missing or unknown value, and sets `data-theme` on `<html>`. `<html>` has `suppressHydrationWarning` because of that. `ThemePicker` reads `data-theme` with `useSyncExternalStore` (the server renders the default), and changes the theme by saving the choice and dispatching a `wordle-theme` event that the script listens for.

**The theme menu** (`ThemePicker.tsx`): a shadcn `DropdownMenu` opened by an icon `Button` (lucide `Palette`, `aria-label="Theme"`). Its content is one `DropdownMenuRadioGroup`: the Light palettes under a "Light" label, then the Dark ones under "Dark"; the current choice is checked. Choosing an item saves its id and dispatches the event. It sits at the top of the sidebar, beside the site title; on phones that row is the top bar, where it sits next to the Articles button, so it is reachable without opening the menu.

**The language toggle** (`LanguageToggle.tsx`, in the sidebar header beside the theme menu on every width, so on phones it sits in the top bar next to the menu button): a bordered group of two options, "EN" and "ไทย", labelled with the page text `language` (so its accessible name is in the page's language). The current language is a plain `aria-current` span; the other is a `Link` to the same page in that language, from `switchTarget(pathname, to, translatedSlugs)` (which goes through `pathIn`). `SiteDocument` computes `translatedSlugs` from `content("th")` (the Articles with `translated: true`), so nothing lists slugs by hand. A Thai page exists for the home page, `/openers`, `/opener-split` and a translated Article only; otherwise (an English Article with no Translation, or a page like `/type-lab`) the Thai option is a disabled, still-focusable `aria-disabled` element, never a link, with a short visible note under the toggle ("Not in Thai yet", described by the group). Clicking a link saves the target language in `localStorage` (`wordle-language`, `LANGUAGE_STORAGE_KEY`) inside `try/catch`. **Remembered means recorded, not applied:** every page already shows its own URL's language and every link on it points into that language, so nothing needs to read the saved value and nothing does; there is no redirect, by it or by browser language. If a language-less entry point is ever added, it may read it.

## shadcn/ui

The generic controls are shadcn/ui components (Radix base, `radix-nova` style) in `src/components/ui/`. They are our files: edit them freely, they are not regenerated. `components.json` holds the CLI config (aliases `@/components`, `@/components/ui`, `@/lib/utils`; `tailwind.config` empty because Tailwind 4 is CSS-first; lucide icons).

**Adding a component.** Use the pinned CLI version (at least 7 days old; check with `npm view shadcn time --json`; currently 4.21.4) from `app/frontend/`:

```
bunx shadcn@4.21.4 add <component>
```

Then fix up what the generator writes, because it targets the default palette: (1) if it adds a `cn` package to `package.json` or imports `from "cn"`, run `bun remove cn` and import `cn` from `@/lib/utils`; (2) replace `bg-accent`, `bg-muted`, `text-accent-foreground`, `text-muted-foreground` with `bg-highlight-med`, `bg-highlight-low`, `text-text`, `text-meta` (see below); (3) remove `dark:` variants, `shadow-*` and `ring-*` utilities (focus is the global outline, borders are `border-rule-strong`); (4) use the radius utilities (`rounded-sm`) and the UI sans. If the CLI adds dependencies, check they went in through bun (7-day rule) and, if `init` or `add` rewrote `globals.css` or `layout.tsx`, discard those changes (it appends its own palette and a Geist font).

**How the variables map.** `tokens.css` defines shadcn's variables on `:root` from our roles, and registers the Tailwind colours for them: `--foreground` and `--popover-foreground` are `text`, `--primary` is `text` (with `--primary-foreground` `background`), `--secondary` is `highlight-low`, `--popover` is `overlay`, `--card` is `background`, `--muted-foreground` is `meta`, `--border` is `highlight-med` (the rule), `--input` is `highlight-high` (rule-strong), `--ring` is `accent`, `--destructive` is `error`, `--radius` is 3px. Our `accent` and `muted` roles keep their meaning, so shadcn's hover fill and quiet fill are written in the components as `bg-highlight-med` and `bg-highlight-low`. There is no `.dark` class: the `dark:` variant is declared but never matches, and each of the ten palettes sets the roles, so every component follows the theme. `--shadow-*` are `none`. Charts, tiles and prose do not use shadcn.

**Where each is used.** `Button`: Widget controls, Prev/Next in the Step-through Game, "Start over" in the State input, the sort headings of the Opener table, the phone menu button, the theme button. `Label`: the labels of `WordRow` and `Field`. `Input`: the Opener table's "Rows to show" field (the word and State fields are `WordRow` and `StateBoard`, below). `Select`: the Strategy of each Side-by-side Game board (the Step-through Game's Strategy choices are `StrategyPicker`, below). `Table`: the Opener table, the Benchmark table, the Step-through Suggestions. `Tooltip`: no component uses it now (`<Term>` and `<Mark>` cards are a Radix `Popover` in `TermTip.tsx`). `Checkbox`: the Opener Distribution's "Only Openers on the Answer List" filter (a Radix checkbox: a `rule-strong` box, filled with the accent and a check in the background colour when checked). `DropdownMenu`: the theme menu. `Collapsible`: the phone Article menu. `TooltipProvider` wraps the page in `layout.tsx`.

## Article layout and `<MarginNote>`

An Article is two columns, in the style of Tufte's books: the text column at the measure and, to its right, a margin for **Margin notes** (see the glossary).

```
| paragraphs, lists, headings, quotes, display maths (68ch) | Margin notes (16rem) |
| code block / Widget: the text column, the gap and the margin together          |
```

- **Tokens** (`tokens.css`): `--container-measure` (68ch), `--spacing-margin-gap` (2.5rem), `--container-margin` (16rem), and `--container-article`, their sum, which is the width of the Article body (`.article-body`, the prose `div`). Text blocks keep `max-w-measure`; display maths (`.katex-display`) keeps the measure, so a formula stays centred over the text; code figures and Widgets are as wide as the body. They are `clear: right`, so they start below any Margin note above them. `<main>` stays `max-w-page` (68rem): the body (989px at the 18px serif) fits in its 64rem of content, so the page container was not widened and the home page did not change.
- **Breakpoint: a container query, not a media query.** `<article>` is a size container named `article` (`container: article / inline-size`), and the margin appears at `@container article (min-width: calc(68ch + 2.5rem + 16rem))`, which is 989px: 68ch is 693px in Newsreader at 18px, plus 40px, plus 256px. What decides whether the margin fits is the width of the Article column, which depends on the sidebar (a column from `lg`, a top bar below it), the page gutters (1.25rem, 2rem from `sm`) and the `max-w-page` cap, not on the window. A media query would have to repeat all of that and would be wrong in the 996 to 1023px range, where the sidebar is a top bar and there is room. In practice: the margin shows from a window width of about 1277px (989 + the 224px sidebar + 64px gutters), and also at 996 to 1023px, where the sidebar is a top bar; at 1024 to 1276px, and on phones, the page is one column. Custom properties cannot be used in a container condition, so the sum is written out in `globals.css`; if a token changes, change it there too.
- **`<MarginNote>`** (`components/prose/MarginNote.tsx`; no import in MDX). Children: short prose, which may hold `<Term>`, `<Word>`, `<Letter>`, `<Mark>`, inline maths and links. No props. It renders `<span class="margin-note">` (a span so it is valid inside a paragraph), in the UI sans at `text-sm` in the `meta` colour, no box, no `aria-hidden`; it stays in the reading order where it is written. Write it on one line (a multi-line note's single `<p>` child is unwrapped, but keep it short), at the end of the sentence or paragraph it belongs to, or on its own line right after a block.
  - **Wide** (the container is at least 989px): a note inside a paragraph is `float: right; clear: right` with a negative right margin of the margin width plus the gap (Tufte CSS), so it sits in the margin level with the line it is written on, takes no room from the text, and a later note is pushed below an earlier one. A note on its own line right after a paragraph, list, quote or display formula is wrapped with that block by `lib/content/rehype-margin-notes.mjs` (a rehype plugin, last in `next.config.ts`; `.margin-row`, a two-column grid) so the two share a row: the note is level with the block (centred on a display formula), and a note taller than its block pushes what follows down. The plugin is given by absolute path (`@next/mdx` resolves plugin paths with `require`). Turbopack's build cache does not track the plugin file, so after editing it delete `.next/cache/turbopack` before `bun run build`.
  - **Narrow**: the note is a block in the text flow, at the measure, indented with a left rule (`rule-strong`), right after the text it was written in (a note in the middle of a paragraph splits that paragraph, so put it at the end). Code blocks and Widgets use the column width; there is no sideways scroll at 390px.
- Header, Prerequisites, "Builds on this Article" and the Prev/Next links are `max-w-measure`, aligned with the text column.

## Design tokens

The look is a minimal editorial one: the text leads and chrome recedes. All non-colour tokens live in `app/tokens.css` (with the role-to-colour mapping, formerly in `globals.css`); the palettes stay in `themes.css`. Components use the Tailwind utilities the tokens generate and no raw sizes, fonts or colours.

- **Fonts** (`next/font/google` in `layout.tsx`, self-hosted at build, exposed as `--font-newsreader`, `--font-inter`, `--font-jetbrains-mono` and mapped to `font-serif`, `font-sans`, `font-mono`): Newsreader for prose, headings and the body default, loaded with its optical-size axis (`axes: ["opsz"]`) so display headings and small notes each get the cut drawn for their size; Inter for UI (sidebar, Widgets, tables, eyebrow labels) and, as `font-tile` (bold), for every letter tile and `<Mark>` label, as Wordle draws its tiles; JetBrains Mono for code, Feedback digits (`22221`) and words shown as data (Openers and Answers in tables). Numbers in tables and Widgets are the surrounding sans with `tabular-nums`, not mono. A throwaway, unlinked page, `/type-lab` (`app/type-lab/`, `noindex`), renders an Article passage, a Margin note, Boards and the Benchmark chart in three pairings (the current one; Source Serif 4, Source Sans 3 and Source Code Pro; Literata, IBM Plex Sans and IBM Plex Mono) with a switch that points the font variables at the other families; delete it once a pairing is chosen.
- **Type scale**: `text-xs` to `text-4xl`, each with a line-height (`--text-*--line-height`). `text-base` is the 18px prose size at 1.7 leading. `tracking-tight` for display sizes, `tracking-caps` for small uppercase labels.
- **Space**: Tailwind's scale for small gaps, plus `gutter` / `gutter-wide` (page padding), `flow` (between blocks), `figure` (around a Widget) and `section` (between sections), as `px-gutter`, `my-figure`, `space-y-section`.
- **Measure and page**: `max-w-measure` (68ch) for prose and text blocks, `max-w-page` (68rem) for the page, `--container-nav` for the sidebar column.
- **Rules**: `border-rule` (`highlight-med`) is the hairline for frames, dividers and the chart grid; `border-rule-strong` (`highlight-high`) for input borders and table heads. 1px (`--rule-width`).
- **Shape**: radius 1-3px (tiles keep 3px), `--shadow-*` are `none`.
- **Focus**: one global `:focus-visible` ring (2px `accent`, 2px offset); components do not restyle it.
- **Scrollbars**: one global style in `globals.css`: `scrollbar-width: thin`, a transparent track and a `highlight-high` thumb that turns `meta` while the box is hovered, so every scroll box follows the palette. Safari, which lacks `scrollbar-color`, gets the same look from `::-webkit-scrollbar` rules (8px, rounded thumb).
- **Colour use**: `text` and `background` carry the page (headings are `text`, not `heading`: `heading` and `accent` fall under 3:1 on `background` in Rosé Pine Dawn and Catppuccin Latte); `accent` is only link underlines, the Term underline and focus. Small metadata uses the derived `text-meta` (`subtle` mixed 45% toward `text`, so it stays above about 4.5:1 in every palette); plain `subtle` is for placeholders and `muted` only for decoration. `surface` is used only behind the video embed and `overlay` for tooltips.
- **Shared utilities** (in `tokens.css`): `link`, `eyebrow` (small uppercase UI label). Inputs, selects, buttons and tables are the shadcn components (see "shadcn/ui"). A Widget is `WidgetFrame` in `widgets/ui.tsx`: hairline rules above and below and an `eyebrow` title (`hideTitle` leaves it out where the page heading says it, as on `/openers`), its content a `ControlPanel`, no fill. Charts use `CHART_CLASS` (UI sans, `text-meta`, tooltip variables) and `CHART_THEME` (grid in `highlight-med`).
- **Prose** (`prose-theme` in `globals.css`) takes fonts, sizes and colours from the tokens; its rules skip `not-prose` blocks (Widgets). KaTeX is sized at 1.08em and long display maths scrolls inside itself.

## Languages

The site has a Thai Translation of the Series under way (`.scratch/thai-translation/spec.md`). English is the original. Thai has the home page `/th`, `/th/openers` and a Translation of every Article (`/th/articles/<slug>`), each with a Thai sidebar and page text. The "EN" tag and the English fallback link stay in the code for any Article that has no Translation (none today). The pieces:

- **The language argument.** `Language` (`en` | `th`, `lib/i18n/language.ts`) is an argument that defaults to `DEFAULT_LANGUAGE` (`en`) on every language-aware function, so existing callers are unchanged: `content(lang)`, `glossary(lang)`, `lookupTerm(term, lang)`, `lookupMark(kind, lang)`, `pageText(lang)`, and the views `SeriesPage`, `ArticleView` and `OpenersView` (each takes `lang`). 
- **`content(lang)`** returns the same shape as before. Reading the files (`read()`) is separate from the pure `buildContent(raw)`, which validates and assembles the Series, Parts, Articles and backlinks from already-parsed frontmatter (tested on inline data in `content.test.ts`).
- **The language reaches `<Term>` and `<Mark>` through the MDX components, not a global.** `componentsFor(lang)` in `mdx-components.tsx` returns the components with `<Term>` and `<Mark>` bound to the language; a view passes them to the MDX body (`<Body components={componentsFor(lang)} />`). They hand `lang` to `TermTip`, which uses it for the glossary behind its nested cards. The `*.mdx` module type (`mdx.d.ts`) accepts the `components` prop.
- **The path helper** (`lib/i18n/paths.ts`, pure): `pathIn(path, lang)` swaps a path between languages (`/articles/x` and `/th/articles/x`, `/` and `/th`, `/openers` and `/th/openers`, in both directions, so it round-trips), `languageOf(path)` reads the language of a path, and `articlePath(slug, lang)`, `homePath(lang)`, `openersPath(lang)`, `openerSplitPath(lang)` and `followPath(lang, params)` (which also writes `params` as the query string) build the pages' paths. Every internal link the pages and the sidebar build goes through it. (Links written inside MDX prose are part of the content, so a Translation writes its own.)
- **The page text table** (`lib/i18n/page-text.ts`): the English words around the content (the Series eyebrow, "Part N", "Prerequisites", "Builds on this Article", the prev/next label, "Explore", "Opener Distribution", "Opener Split" and "Follow an Answer" each with its intro, help text and labels, "How it works", "Watch from m:ss", the sidebar's nav label and Menu/Close) in one `PageText` object keyed by name, some keys functions for the parts that vary. `PageText` is a type, so a second language's table must have every key. `Sidebar` (a Client Component) takes a `lang` and calls `pageText(lang)` itself, since functions cannot be passed from a Server Component. The Opener Distribution page's two paragraphs and the theme menu are not in the table yet.

- **Thai routes and `<html lang>`.** English and Thai are two route groups, `(en)` and `(th)`, each with its own root layout (there is no top-level `app/layout.tsx`); both render `SiteDocument` with their `lang`, so `<html lang="en">` or `<html lang="th">` is in the static HTML of every page (the Thai pages are `app/(th)/th/page.tsx` and `th/openers/page.tsx`, both statically generated). Navigating between the two groups is a full page load, which is what changes `<html lang>`.
- **The Thai Series file** `content/th/series.mdx` holds only frontmatter: `title`, `intro` and `parts` (`id`, `title`, `intro`). `buildContent(raw)` takes an optional `translation` (its Series file and the Articles translated so far) and lays it over the English content: the Series title and intro and each Part's title and intro are replaced, and the build fails when the Thai Part ids are not the English ones in the same order. Each `Article` has `translated`: always true for English, and for Thai true only for an Article with a Translation (its title and summary replaced; Prerequisites, Part and number always come from English); an untranslated one keeps its English text. `articleLink(article, lang)` in `lib/i18n/paths.ts` is the link to use: the Article in `lang`, or the English page when `translated` is false.
- **The "EN" tag** (`EnTag`, text from page text `enTag` and `englishOnly`) follows an untranslated Article's title in the sidebar and in each Part's list.
- **Thai fonts and line height.** `lib/theme/fonts-thai.ts` loads Noto Sans Thai Looped (`subsets: ["thai"]`, variable weight) with `next/font`, and only the Thai layout imports it, so English pages do not load it. `tokens.css` lists `var(--font-noto-thai-looped, <fallback>)` after the Latin family in the serif, sans and tile stacks, so Thai letters use it and Latin letters keep Newsreader or Inter; on English pages the variable is undefined and the fallback stands in. `:root:lang(th)` in `tokens.css` raises every step of the line-height scale (body 1.8, headings 1.3 to 1.55) so stacked vowels and tone marks are not clipped.
- **Screenshots.** `bun run screenshot` with no paths also shoots `/th`, every translated Article, `/th/openers`, `/th/opener-split` and `/th/follow?answer=watch&step=2`; the English pages include `/opener-split` and `/follow?answer=watch&step=1` and `step=4` (the shots are of the top of the page: the inputs and the start of the strip).

### Translations

A Translation of an Article is `content/th/articles/<same file name as the English one>.mdx` (`01-rules.mdx`). Its MDX body is written with the same components as English; its frontmatter holds only:

```yaml
title: "กติกา"
summary: "..."
source: fad7f9922ce97020d0736a090eea2a23db6fcc59   # git hash-object content/articles/01-rules.mdx
```

Prerequisites, Part, number and `video` are never read from it. `/th/articles/<slug>` (`app/(th)/th/articles/[slug]/page.tsx`, the same `ArticleView` with `lang="th"`, importing the body from `content/th/articles/`) is generated only for Articles that have a Translation; a Prerequisite link, backlink or prev/next link on a Thai page goes to the Thai page when there is one and otherwise to the English page, followed by the "EN" tag.

**To add a Translation:** write the Thai file, keep every Widget, `##` heading and code block exactly as in English, set `source` to `git hash-object <English file>`, and run `bun test` and `bun run build`. When the English file later changes, the build prints `warning: ... has changed since this Translation was made`; review the Translation, then set `source` to the hash it prints. A stale hash never fails the build.

**What the build enforces** (`lib/content/translation.ts`, pure, tested in `translation.test.ts`; `content.ts` runs it while reading `content/th/articles/`): `checkTranslation(file, english, translation)` throws, naming the file and the first mismatch, when the Widgets differ (every capitalised tag except the prose components `<Term>`, `<Word>`, `<Mark>`, `<Letter>`, `<MarginNote>`; tag, props including `id` in any order, and order of appearance), when the number of `##` headings differs, or when a fenced code block differs in any character (title line, comments and docstrings included). Fenced and inline code text is otherwise ignored. It compares structure, not meaning. `buildContent` fails on a Thai file with no English Article, one whose name is not the English file's, or a missing or empty `title` or `summary`. `staleWarning` compares `source` with `blobHash` (git's blob hash) of the English file.

**The Thai glossary** `content/th/glossary.json` has the same shape as `content/glossary.json` and must have exactly its term names (the English names are the keys; `checkGlossary` throws on a missing, extra, repeated or empty term when the Thai glossary is first used, so the build fails). Definitions are Thai with the other terms in English, so `splitDefinition` links them unchanged and cards nest. The Mark entry keeps `**Correct** (…)`, `**Present** (…)`, `**Absent** (…)`, which `parseMarkKinds` reads, so Mark cards show Thai definitions. Add a term to both files together.

## Series and Articles

Content lives in `content/`, outside `src/`. The site has exactly one Series, "Solving Wordle" (`content/series.mdx`), and every Article belongs to it. Every page is statically generated (`generateStaticParams`, `dynamicParams = false`), so an unknown URL is a 404.

**MDX pipeline.** `next.config.ts` wraps the config in `@next/mdx`. The remark and rehype plugins are named by string with serialisable options (`"remark-frontmatter"`, `"remark-math"`, `["rehype-katex", {...}]`), because Turbopack cannot be handed functions. `app/layout.tsx` imports `katex/dist/katex.min.css`. KaTeX is set to throw on bad maths, so a typo in a formula fails the build.

**Frontmatter.** `remark-frontmatter` only strips the `---` block from the rendered output. The data is read by `lib/content/content.ts` with gray-matter, straight from the files with `fs`. That gives the index, the backlinks and the validation one plain function over all files, with no need to compile and import every MDX file to read a few fields.

**Add or reorder an Article.** The file name is `NN-slug.mdx`: the two-digit prefix is the Article's number (and its place in the Series), the rest is its URL slug (`05-candidate-set.mdx` is `/articles/candidate-set`). Prerequisites use the slug without the prefix, so renumbering never breaks a link or a Prerequisite. To insert or move an Article, rename files so the numbers run 01..N again (`git mv`). There is no `order` field. Create `content/articles/NN-<slug>.mdx`:

```mdx
---
title: "Feedback Split"
summary: "One line shown in lists."
prerequisites: [candidate-set]   # slugs of other Articles, or []
part: solving-wordle             # id of a Part in series.mdx, required
video: "4:10"                    # optional: where it starts in the Series video ("m:ss", "h:mm:ss" or seconds)
---

Body in MDX. Inline maths $x^2$, display maths in `$$ ... $$`, and <Term>Feedback Split</Term>.
```

The Article page header shows its Part and number (`Part 2 · Solving Wordle · 05`), then its Prerequisites (from `prerequisites`), the Articles that list it as a Prerequisite ("Builds on this Article", the backlinks), and previous and next links across all Articles in number order.

**Sidebar** (`components/site/Sidebar.tsx`, rendered by `layout.tsx` on every page; there is no top header). Top to bottom: the site title (the Series title, a link home) with the theme menu button beside it, then the Articles grouped under their Part titles (`Part 1 · Wordle`, then number and title each), then an "Explore" heading below the Parts with links to `/openers` ("Opener Distribution"), `/opener-split` ("Opener Split") and `/follow` ("Follow an Answer"), in that order, each `aria-current="page"` on its own page. The current Article has `aria-current="page"` (found with `usePathname`, so it is a Client Component) and is styled `border-text font-medium text-text`. From the `lg` breakpoint (1024px) it is a column (the layout grid is `--container-nav` + the rest): `position: sticky`, full viewport height, and the Article list scrolls inside it if long. Below `lg` it is a compact top bar with the title, the theme button and a "Menu" button (a shadcn `CollapsibleTrigger`, which sets `aria-expanded` and `aria-controls`) that opens the Articles and the Explore link below the bar; it closes by itself after navigating. The `CollapsibleContent` is force-mounted and always shown from `lg`. It is one markup, so CSS only decides what is shown, and the page never scrolls sideways. `<main>` is `max-w-page`. On an Article page the column holds text at the measure (68ch) plus a margin for Margin notes, and Widgets and code blocks span both (see Article layout below). The home page text stays at the measure.

**The Series** (`content/series.mdx`): frontmatter `title`, `intro`, `parts` and optional `video` (a YouTube id or URL), then optional MDX body text. The home page `/` is the Series page: the title, intro and video (if any), then each Part (number, title, intro) with its Articles in number order, each with its number, title and summary, plus a "Watch from m:ss" link when both the Series and the Article have a video time. After the Parts comes an "Explore" section (an `h2` styled like a Part heading, with a one-line intro): one entry per Explore page in the sidebar's order, in the same ruled list look as the Articles: the page name as a link, one sentence on its purpose, three short points on what to explore there, and a "Builds on" line linking the Articles it builds on (Opener Distribution: 11; Opener Split: 06 and 07; Follow an Answer: 08). There is no `/series/...` route.

**Parts.** `parts` is an ordered list of `{id, title, intro}`. The Series has two: `wordle` (Part 1, Articles 01-03: the game) and `solving-wordle` (Part 2, Articles 04-10: the road to the best Opener). Every Article names its Part's `id` in `part`, and the file numbers run through the whole Series, so a Part's Articles are consecutive.

**Numbering.** An Article's number is the `NN` of its file name (1 to 11), and `lib/content/parts.ts` `formatNumber` is the one formatter: always two digits with leading zeros (`01` ... `11`). It is shown in the sidebar, on the home page, in the Article header and in the previous/next links, always in `font-mono` with tabular figures.

**Video timestamps.** An Article's `video` is a start time in the Series' video. Only the Series page uses it, as a "Watch from m:ss" link to YouTube (`&t=<seconds>s`) beside each Article; the Article page itself shows no video. An Article without `video`, or a Series without one, has no link; none of the current content has a video yet (ticket 10).

**Build-time checks** (`lib/content/content.ts`; a failure stops `bun run build` with the file name in the message): unknown Prerequisite, an Article that is its own Prerequisite, a Prerequisite cycle, the file names (`parseArticleFiles`: not `NN-slug.mdx` with exactly two digits, a repeated number, a repeated slug, or numbers that are not exactly 01..N with no gaps), and missing or malformed frontmatter. Parts (`lib/content/parts.ts` `validateParts`): an Article without `part` (`frontmatter "part" is missing`), an unknown Part (`unknown Part "x". ## `<Term>`

`<Term>Candidate Set</Term>` works in any MDX file with no import (`src/mdx-components.tsx`). It looks the term up, case-insensitively, in `content/glossary.json` (through `lib/content/glossary.ts`), a list of `{term, definition}` entries. The JSON is a copy of the repo's root `GLOSSARY.md` (each `**Term**:` and its definition lines, without `_Avoid_:` lines); the frontend never reads `GLOSSARY.md`, so when a term is added or reworded there, copy it into the JSON by hand. It renders underlined text with the definition in a card, a Radix `Popover` (`TermTip.tsx`, a Client Component; `Term` itself stays a Server Component that reads the glossary). The card opens on hover (after 150 ms, closing 250 ms after the pointer leaves the term and its card), on keyboard focus (`tabIndex=0`, `role="button"`) and on tap (a tap toggles it; a mouse click pins a hovered card); Escape or a tap elsewhere closes it. **Cards nest**: `splitDefinition` (`lib/content/glossary.ts`) links the first mention of every other glossary term in a definition (whole words, case-sensitive, plurals such as "Guesses" and "Strategies" included, the longest term first so "Candidate Set" beats "Candidate", bold runs left alone), and each link is itself a `TermTip`, so hovering "Game" and then "Guess Limit" in its card opens a second card over the first. A card does not link its own term or the terms of the cards it sits in (a React context). The pointer can move from a term into its card and on into nested cards without closing them, because React counts a portalled card as inside its parent. Enter or Space on a term opens its card with the focus on the card's first term (or the card), so the keyboard can walk the nesting; Escape closes the innermost card and returns the focus to its term. `<Mark>` uses the same card, and a bold Mark name in a definition (the Mark entry's **Correct**, **Present** and **Absent**) is drawn in a card as that Mark's coloured label with its own card, as `<Mark>` draws it (the label classes are shared in `components/prose/mark-style.ts`). When the shown text differs from the term, name the term: `<Term of="Candidate">candidates</Term>`.

A term that is not in the glossary throws while the page is prerendered, so `bun run build` fails with `<Term>: "..." is not defined in content/glossary.json`. In `next dev` the error shows on that page.

## `<Mark>`

`<Mark kind="correct" />` (also `present`, `absent`) works in any MDX file with no import. It renders the Mark's name, or its children (`<Mark kind="present">Present letters</Mark>`), as a small inline label: JetBrains Mono, `text-xs` semibold caps with `tracking-caps`, tile radius (`rounded-md`), `px-1.5`, `leading-none` so it does not grow the prose line, on `bg-correct` / `bg-present` / `bg-absent`. It is a label, not a button (no hover fill, `cursor-help` only). On hover, keyboard focus and tap it shows that Mark's definition through the same `TermTip` as `<Term>` (`Mark.tsx` passes its own trigger classes). `lib/content/glossary.ts` `parseMarkKinds` splits the Mark entry of `content/glossary.json` into one definition per kind: the parenthetical after each bolded `**Correct** (...)`, `**Present** (...)`, `**Absent** (...)`; a missing one, or an unknown `kind`, throws and fails the build (`<Mark>: unknown kind "green"...`). Tests: `lib/content/glossary.test.ts`.

**Contrast.** The palettes' `on-*` roles are tuned for big tile letters. Against their Mark colour, small text reaches 4.5:1 in only 15 of 30 cases (correct, present, absent; worst: Nord absent 1.96, Rosé Pine Dawn present 2.05, Tokyo Night absent 2.17). So the label text is not `on-*`: tokens.css derives `ink-correct`, `ink-present`, `ink-absent` (`text-ink-*`), black or white by the lightness of the Mark colour (relative colour, threshold OKLCH L 0.6). The better of black and white is always at least about 4.5:1; across the ten palettes the lowest is 4.51 (Flexoki Light correct), most are above 6. The palettes are untouched. Tiles still use `on-*`.

## `<Word>`

`<Word>speed</Word>` works in any MDX file with no import. It has three variants, picked with `variant`:

- **`simple`** (the default without Feedback): the word in caps of the surrounding font (the serif in prose, the sans in a Margin note) at `0.82em` with a little tracking, unframed, so it reads as a word and not as a widget. Frames and tiles are kept for words that carry Feedback.
- **`text`**: JetBrains Mono caps at `0.8em` with `tracking-caps`, no frame, for a word shown as data.
- **`cell`** (the default with Feedback): five small letter tiles (bold `font-tile` caps, tile radius, sized in `em` so they do not grow the line), plain tiles with the `rule` frame when there is no Feedback. The tile styles live in `components/prose/letter-tile.ts`, shared with `<Letter>`.

Tiles are what show Feedback, so `simple` or `text` together with `feedback` or `answer` throws, as does an unknown variant. `simple` and `text` are plain text, so screen readers read the word as is. `<Word feedback="00101">speed</Word>` paints each tile with its Mark (digits 0 Absent, 1 Present, 2 Correct), and `<Word answer="abide">speed</Word>` works that Feedback out with `lib/wordle/feedback.ts`. Painted tiles use the same `bg-*` and `text-ink-*` pair as `<Mark>`, for contrast. Screen readers get one `role="img"` label: the word, then each letter's Mark when there is Feedback ("SPEED: S Absent, P Absent, E Present, …"). The word (and `answer`) must be on the Guess List, read at build time from `packages/wordle/src/wordle/data/guesses.txt` by `lib/wordle/words.ts`; an unknown word, malformed `feedback`, or both `feedback` and `answer` throws and fails the build.

**Blanks.** `_` is a blank letter, for a family of words: `<Word>_atch</Word>` shows _ATCH in `simple` and `text`, and an empty plain tile in `cell`. Instead of being on the Guess List, a word with blanks must fit at least one word on it (`fitsPattern` in `lib/wordle/words.ts`, tested in `lib/wordle/words.test.ts`), so a typo such as `_acth` still fails the build. It takes no `feedback` or `answer`. Screen readers get it spelled out as a `role="img"` label ("blank, A, T, C, H").

In prose, write a letter of a word as `<Letter>` (below), not a bare capital, so it reads as a letter and not as text ("the first <Letter>e</Letter>", "none of <Letter>c</Letter>, <Letter>r</Letter>…").

## `<Letter>`

`<Letter>e</Letter>` works in any MDX file with no import: one letter drawn as the same small tile as a letter of `<Word>` (plain, with the `rule` frame). `<Letter mark="present">e</Letter>` paints it with that Mark; `mark` takes the names `<Mark kind>` takes (`correct`, `present`, `absent`). Screen readers get "E" or "E, Present". Anything but one letter a to z, or an unknown `mark`, throws and fails the build.

## `<Boards>` and `<Board>`

Static Game boards, side by side, in any MDX file with no import (`components/prose/Boards.tsx`). `<Boards title="The 11 Losses">` is a figure in the Widget frame (`WidgetFrame`) holding a grid of as many columns as fit (`auto-fill`, at least `9rem` wide, `11rem` from `sm`), so two boards sit side by side on a phone and three or more on a wider page. Each `<Board pattern="_atch" guesses="raise tangy caput batch hatch latch match watch" />` is one Game: the last Guess is the Answer, and every row is painted with its Feedback against it (`scoreFeedback`, worked out at build time; no client code). Rows are numbered, and a dashed `rule` line before the seventh row marks the Guess Limit of six, so a Loss shows as rows under it. The caption is `pattern` as a `<Word>` (optional, blanks allowed), then `label` (optional, an `eyebrow` naming the Search Scope, e.g. "All words"), then the Answer and its Guess Count. `highlight` (optional, space-separated Guesses) rings those rows in `accent` (`ring-2`, offset by the page `background`) and sets their row number in `accent`, for the word a search over All words plays that is not a Candidate; the row's group label gets ", highlighted". A highlight that is not one of the Guesses throws. Tiles are `Tile` with `board` (`h-6`, `h-7` from `sm`); each has its letter and Mark in its `aria-label`, and each row is a group labelled "Guess 7: match". A Guess not on the Guess List throws and fails the build.

## Code blocks

Fenced code in any MDX file is highlighted at build time by `rehype-pretty-code` + Shiki (no highlighter JS reaches the browser; the built HTML has the coloured spans). Write the language, then optional meta:

````
```python title="Two-pass Feedback" {64-69}
...
```
````

- `title="..."` adds a caption row naming the idea the code shows (for example "Two-pass Feedback"), not a file path: the code is there to explain the idea; `{3-5,9}` highlights lines (quiet fill plus an `accent` left rule); every block shows CSS-counter line numbers (`meta` colour, `user-select: none`, so they are not copied); `showLineNumbers` is accepted but no longer needed. No language means plain text. Inline `code` keeps its small `highlight-low` chip.
- **Block style** (`globals.css`, under `prose-theme`): `<figure data-rehype-pretty-code-figure>` with a hairline `border-rule` frame, `highlight-low` fill, `rounded-sm`, no shadow, `font-mono` `text-sm`. Long lines scroll inside the `<pre>` (`overflow-x: auto`), never the page.
- **Copy button**: `mdx-components.tsx` maps `figure` to `CodeFigure.tsx` (a small Client Component) for highlighted figures only: a shadcn `Button` (`ghost`, `icon-xs`, `Copy` then `Check` for 2s, `aria-label="Copy code"`, plus an `sr-only` `role="status"` "Code copied"). It copies the code element's text.
- **Turbopack**: the plugin is named by string in `next.config.ts` and its options are plain JSON. The Shiki theme is a VS Code-format object (`tokenColors`; rehype-pretty-code only takes an inline theme in that shape) whose colours are `var(--code-*)`, so no function (`createCssVariablesTheme`) is needed.
- **Token roles**, defined once in `globals.css` (`--code-*`), each coloured role mixed toward `text` so it stays readable on `highlight-low` in all ten palettes (lowest about 4.1:1 in Catppuccin Latte; most above 5): keywords/storage `accent` 40%; strings `success` 40%; numbers and constants (`True`, `None`) `present` 30%; function names and decorators `heading` 40%; types and classes `error` 40%; comments (italic) and punctuation/operators `meta`; everything else `text`. They follow the theme picker live because they are CSS variables.

## Maths

Write `$inline$` and `$$display$$` (remark-math, rendered by rehype-katex). Prose is styled by `@tailwindcss/typography` as `prose prose-theme`, where `prose-theme` (in `globals.css`) sets the typography from the design tokens. Display maths is capped at the measure (see Article layout), so a formula centres over the text.

## Controls

The same controls appear in Widgets, in Articles and on the standalone pages, so they are shared (`components/controls/`). The page body is serif (Newsreader); a control is UI, so it is Inter (`font-sans text-sm`), and the components below set that themselves rather than relying on a `WidgetFrame` around them. The rule is general: a data or control component (`SplitBars`, `SplitGroups`, `FollowPath`, the Follow page's rows, the Opener Split results) owns its font, with `ControlPanel plain` or `font-sans` on its root, so it looks the same inside a `WidgetFrame` and bare on a page; only page headings and intro prose are the serif.

- `SegmentedControl`: joined radio buttons (a Radix `RadioGroup`; arrow keys move within it). Generic over the option type: `options`, `names`, `value`, `onChange`. Named with `labelledBy` (a visible label's id) or `label`. Used by every `StrategyPicker` row, the Follow page's "Full split / Answer's path" toggle and the Opener Split page's "Blocks / Bars" toggle.
- `InfoTip`: the ⓘ button and its card (a Radix `Popover`): opens on hover, focus and tap, closes on Escape, and stops Left and Right from reaching the Step-through Game's key handler.
- `Field`: a label, an optional `InfoTip`, and the control. `layout="inline"` is a label column (`w-32`) then the control, wrapping the control below the label on a narrow row (the Strategy rows, the Follow page's Answer and Opener); `"stacked"` puts the label above. `htmlFor` makes the label a `<label>` for an input; `labelId` gives it an id for a control that uses `aria-labelledby` (a `SegmentedControl`). With a `WordRow`, pass `hideLabel` (the word row then keeps its `label` as `aria-label`) and the Field's `htmlFor`.
- `ControlPanel`: a wrapper for a group of controls: `font-sans text-sm` and a `gap-4` grid (`plain` keeps only the font). `WidgetFrame` and `StrategyPicker` use it, and so do the toolbars of the Follow and Opener Split pages.

**The label rule.** Every field label is the one `FIELD_LABEL` style (exported from `Field.tsx`, also used by `WordRow`'s own label): sentence case, small sans, `text-meta`. The uppercase `eyebrow` is for section titles only (a Widget's title, table heads), never for a field label. All buttons are the shadcn `Button` at its default size.

## Widgets

Interactive figures, registered in `mdx-components.tsx` (no import needed). They are Client Components wrapped in `<Suspense>` (they read the URL with `useSearchParams`, which a static page needs). Tiles use the theme roles (`bg-correct text-on-correct` and so on); Marks are also in each tile's `aria-label`, so colour is never the only cue.

**Starting state and URL params.** A Widget starts from its MDX props. A URL query param of the same meaning overrides the prop, so a video take can be reproduced from a link. Edits are written back to the URL with `history.replaceState` (the param is removed again when it equals the prop), so the address bar is always a link to the current take. Params are read once, when the Widget mounts.

**Two Widgets in one Article.** Give each an `id`; its params are then named `<id>.<name>` (`fb.guess`, `cs.state`). Without an `id` the plain names are used (`guess`, `answer`, `state`), so two Widgets of the same kind without ids would share state.

### Word and State inputs

Every Guess, Answer and State in the Widgets is typed Wordle-style, with two shared parts.

**`WordRow`** (`widgets/WordRow.tsx`): a word as a row of five tiles. Props: `id`, `label`, `hideLabel`, `value` (letters only, at most five), `onChange(word)`, `onEnter(word)` (Enter with five letters), `onBackspaceEmpty()` (Backspace with nothing typed), `keepFocus` (don't put the phone keyboard away on Enter), `error` (a message, or null), `hint`. It is one focusable control: a visually hidden `<input>` (`sr-only`, `maxLength=5`, `inputMode="text"`, `enterKeyHint="done"`, `autoCapitalize="none"`, `autoComplete="off"`, `autoCorrect="off"`, `spellCheck={false}`, `text-base` so iOS does not zoom) labelled by a `<Label>` drives five `aria-hidden` tiles. Screen readers get the label and the input's value. Pressing the tiles focuses the input (so a tap opens the phone keyboard). Letters fill left to right, anything else is dropped (`cleanWord`), Backspace removes the last, and arrow keys, Home and End are ignored (and the selection is kept at the end, e.g. after Ctrl-A on a Mac), because the tiles have no movable caret. The next tile to fill shows a blinking caret (a pulse, off with `prefers-reduced-motion`) and the focus outline while the row has focus. Enter with five letters calls `onEnter` and, unless `keepFocus`, blurs the input (keyboard away); with fewer it says "Type all five letters." and shakes. `error` turns the tiles red, sets `aria-invalid` and `aria-describedby`, shows the message below (`role="alert"`) and shakes the row once whenever a message appears (the `animate-shake` utility in `tokens.css`, only under `prefers-reduced-motion: no-preference`; the message and the red border carry it otherwise).

**Checking a word.** `useGuessCheck(word)` asks the API whether a five-letter word is on the Guess List, 200ms after the fifth letter (so typing and deleting do not make a request per key), and returns `{ checking, error }`. The question is `GET /api/feedback?guess=w&answer=w` (`checkGuess` in `lib/api.ts`): a word that is not on the Guess List gets a 400 with the message, which `error` carries ("guess 'zzzzz' is not a valid five-letter word"). No new endpoint is needed. The Answer of the Step-through Game is checked by the `GET /api/solve` it already makes, which refuses a word that is not on the Answer List ("answer 'aahed' is not on the Answer List"); its message goes to the row. The Feedback scorer still scores locally at once, so its Marks show as soon as there are ten letters; only the API's word check and its cross-check wait.

**`StateBoard`** (`widgets/StateBoard.tsx`): a State like the gpui app's Solver mode. Props: `rows` (the State), `onChange(rows)`, `label`, `renderRowEnd(row, i)` (something beside each row). It is controlled by the parent, which keeps the rows in a URL param; the Guess being typed is its own. Rows of `Tile`s, then a `WordRow` for the next Guess:

- type a Guess and press Enter: the API checks it is on the Guess List (a refusal shows under the row and shakes it), and the row joins the State with every tile Absent;
- click or tap a tile, or press Space or Enter on a focused one, to move it Absent, then Present, then Correct, then Absent (each tile is a button named like "S, Present"); typing a letter or Backspace while a tile has focus goes to the typing row, so keyboard focus is never trapped;
- Backspace with nothing typed takes the last Guess back into the typing row (its Marks are cleared, as in the gpui app);
- up to six Guesses; a row that is all Correct is a Win ("Every tile is Correct: that Guess is a Win..."), and the typing row goes away; at six Guesses it says so;
- "Start over" (a shadcn `Button`) clears the State.

The logic is pure and tested in `lib/widgets/state-board.ts` (`typeLetter`, `backspace`, `enterGuess`, `cycleMark`, `isWin`, `canType`, `rowsFromState`, `startOver` on a `{ rows, typed }` board; `state-board.test.ts`). `rowsFromState` reads the `guess:feedback,...` text and keeps only five-letter rows, so a partial word in an old link is dropped.

**Keyboard.** Tab reaches each tile button and the typing row's input in turn, and every other control; nothing traps focus. The Step-through Game's Left and Right keys ignore any key pressed in an `<input>`, which includes every `WordRow`, and in the Strategy picker's radio groups, which use the arrow keys themselves.

### Side-by-side Game (Widget 8)

**Side-by-side Game** (`SideBySideGame`, Article 08 with `id="race"`). The Step-through Game for two to four Strategies at once, animated and looping. Props: `answers` (comma separated, default `watch,goner,pound,wight,crane`), `strategies` (two to four Strategy ids, default `bits-answers-candidates,bits-guesses-candidates,bits-guesses-all`), `interval` (milliseconds per beat, 200 to 5000, default 900), `id`; URL params of the same names override them. All boards have `max(6, longest Game)` rows with a dashed rule after the sixth. After the longest Game and `HOLD_BEATS` (3) more beats it moves to the next Answer, and after the last starts over; the Answer is shown as `?????` until every board is done. It plays only while on screen (an IntersectionObserver); with `prefers-reduced-motion` it starts paused and tiles do not flip. Controls: an Answer `WordRow` (a full word loops that one Answer), Play/Pause, previous and next Answer, Restart, and per board a Strategy Select (grouped by Ranking, a Strategy already on a board disabled), a remove button (above two boards) and "Add a Strategy" (below four). ### Opener table and Benchmark chart (Widgets 5 and 6)

Both load their data once with the `useLoad` hook (`GET /api/openers`, `GET /api/benchmark`); a 503 from a backend that was not precomputed shows its message (including "Run `just precompute-benchmark` first.") as the error.

**Opener table** (`OpenerTable`). Props: `top` (default 20, 1 to 500), `highlight` (comma separated words, e.g. `"crane,slate"`), `id`. URL params `top`, `highlight` (`op.top` with `id="op"`) override the props. A table of rank, Opener, bits, Expected Candidates, groups, largest group and Candidate?. Every heading is a button that sorts by that column (click again to reverse; `aria-sort` is set). Highlighted words are emphasised and listed even when they rank below `top`; when `highlight` is set the Widget fetches all 500 rows. The table scrolls horizontally inside its card at phone width. A "Rows to show" input edits `top`.

**Benchmark chart** (`BenchmarkChart`). Props: `strategies` (comma separated Strategy ids, e.g. `bits-answers-candidates,bits-guesses-all`; default all eight; unknown ids, the old version 1 ids included, are dropped, none valid means all), `id`. URL param `strategies` (`bm.strategies`) overrides it. Above the chart a picker of checkboxes, one fieldset per Ranking (Expected Information, Expected Candidates; `STRATEGY_GROUPS`), each box named by its Guess Pool and Search Scope ("Answer List, Candidates only") with its colour swatch; ticking one rewrites `strategies` in the API's order (`toggleStrategy`), and the last ticked box is disabled so the chart is never empty. Above the picker a tab row (`COMPARISONS`) ticks a preset to compare: All, or the four Strategies that share one Ranking, Guess Pool or Search Scope (Expected Information, Expected Candidates, Answer List, Guess List, Candidates only, All words), each with a caption naming what the other two choices change; the current tab is the one whose Strategies are exactly the ticked ones (`comparisonFor`), else none. The picker lists only the Strategies `benchmark.json` holds. The chart is grouped bars (`barY` with `layout: group()`, `z` = Strategy): x is the Guess Count 1 to 6 plus a final "Lost" group for the Losses, so Losses are on the chart and not folded into the distribution; y is Games. Each Strategy has a fixed colour by its id (`strategyColor`), so it keeps it when a subset is shown: one theme role per Guess Pool and Search Scope (`--accent` for Answer List, Candidates only; `--present` for Answer List, All words; `--error` for Guess List, Candidates only; `--correct` for Guess List, All words), as it is for Expected Information and mixed half with `--background` for Expected Candidates, so the two Rankings of one Guess Pool and Search Scope share a hue. A last table (`GUESS_SOURCES`) says, for each Guess Pool and Search Scope, which words the Opener and every later Guess may be, so it shows that Guess List with Candidates only guesses only Answer List words after the Opener; its caption adds that both Rankings play each pair and that every Strategy guesses Candidates only with two or fewer Candidates left. `pickStrategies`, `toggleStrategy`, `strategyColor`, `COMPARISONS` and `comparisonFor` are tested in `widget-helpers.test.ts`. ### Opener Distribution (Widget 7)

`OpenerDistribution` (`components/widgets/OpenerDistribution.tsx`) charts the [Guess Count Matrix](guess-count-matrix.md) for one Strategy: how many Openers have each Average Guess Count, rounded to two decimals. It loads `GET /api/guess-counts?strategy=<id>` once per Strategy with `useLoad`; a 503 shows the API's message (it says to run `just precompute-guess-counts` or `just restore-cache`). When `complete_rows` is below `total_rows` it charts what there is and says "N of 14,855 Openers played" (2,315 for an Answer List Strategy: `total_rows` is the size of its Guess Pool). It is registered in `mdx-components.tsx`, so Articles can embed it.

**Props and URL params** (all overridden by the URL param of the same name, `od.strategy` with `id="od"`): `strategy` (one of the eight ids, default `bits-guesses-all`; an id the API does not know, an old version 1 id such as `bits-all` included, shows its 400 message), `answersOnly` (chart only Answer List Openers, default false; URL value `true`), `highlight` (a comma separated word list, the one field for highlighting and searching; non-five-letter words are ignored, and there is no `find`), `controls` (default true; false hides every control and leaves the props and URL params in force, the stat cards and the bar list stay), `tabs` (default false; URL value `true`, see Highlight tabs), `id`.

**Controls** (above the chart; with `hideTitle`, which the `/openers` page sets, the frame's "Opener Distribution" title is left out as it repeats the page heading, and Article 11 keeps it): the Strategy picker, then "Highlight words, comma separated" (a stacked `Field`; the `highlight` list; spaces also separate) and an "Only Openers on the Answer List" checkbox (the `answersOnly` filter, named so it is not taken for the Answer List Guess Pool; a shadcn `Checkbox`, accent when checked, with "Answer List" a `<Term>`).

**Strategy picker** (`components/widgets/StrategyPicker.tsx`, shared with the Step-through Game and the Follow page; each row is a `Field` (inline) around a `SegmentedControl`, see "Controls"), laid out like the gpui app's Solver panel: three rows of joined buttons, **Guess Pool** (Answer List, Guess List), **Search Scope** (Candidates only, All words) and **Ranking** (Expected Information, Expected Candidates), with the glossary's names (`POOL_NAMES`, `SCOPE_NAMES`, `RANKING_NAMES`, and the option orders `POOLS`, `SCOPES`, `RANKS` in `lib/wordle/strategies.ts`), then "Strategy: <display name>". After each row's label is an ⓘ info button (accessible name "About Guess Pool" and so on) whose card, a Radix `Popover` in the look of a `<Term>` card, says in one line what the choice decides and then one line for each option; it opens on hover, keyboard focus and tap, closes on Escape, and sits outside the radio group so the arrow keys stay the group's (the button and its card also stop Left and Right from reaching the Step-through Game). The picker takes an optional `lang` (default English) and reads the row labels, the "Strategy" label and the card text from the page text table (`pageText(lang)`: `guessPoolLabel`, `guessPoolTip`, ... in both languages; the Widgets do not pass it yet, since MDX Widgets have no language). Each row is a Radix `RadioGroup` (`role="radiogroup"`, arrow keys move within it, Tab to the next row); the chosen button is on `--highlight-med`. A row's label sits left of it, or above it when the row would not fit (a phone). The Opener Distribution stores the three choices as one `strategy` id (`strategyFor`; an unknown id in the URL shows the default choices and the API's 400 message); the Step-through Game keeps its `pool`, `scope` and `by` params. The checkbox filters on the client (`filterOpeners`) and makes no request; the Strategy picker is the only control that fetches.

**Chart.** It is custom SVG, not TanStack Charts: one `<rect>` per Opener (up to 14,855), because the stack must show each Opener as its own block. x is the Average Guess Count in bars 0.01 wide, labelled every 0.05; y is the number of Openers, with a round tick step. Each bar stacks its Openers in rank order, best at the bottom. Blocks are filled by Answer List membership in theme roles: `--correct` on the Answer List, `--present` off it; highlighted Openers are `--accent` with a `--text` outline, and their word is printed above their bar with a leader line (labels whose bars are closer than 40 units go on separate rows, `labelRows`; the top margin grows to fit them). The blocks are a memoised component, so a tooltip change does not render 15,000 rects again.

**Fixed size, fitted Y axis.** The SVG keeps its size when "Only Openers on the Answer List" flips (plot height 320 units, the label headroom from every Opener's highlight rows). The x range (first to last occupied bar) comes from every Opener of the Strategy, so bars never move sideways; the Y axis (tallest stack and its round ticks) comes from the Openers shown, so the filtered bars fill the plot (`chartDomain`, `groupOpeners(openers, domain)`; block height is the plot height over the Y maximum). Checked in a browser: the same bounding box before and after, and the top tick changes (800 to 125). Changing the Strategy loads other data and may rescale.

**Tooltip.** Hovering a block with a mouse shows its word, rank (of the Openers played), Average Guess Count (3 decimals), Losses and Answer List yes/no. A tap (or a click) on a block pins the tooltip to it (and selects its bar, below); tapping another block moves it and tapping elsewhere clears it. One `pointermove` / `click` handler on the `<svg>` reads the block's `data-word`; the tooltip is a positioned `div` inside the scrolling frame (above the block, below it near the top, kept inside the chart's width). The pinned tooltip is re-measured after layout changes, since opening the side column narrows the chart.

**Bin counts.** Hovering anywhere in a bar's column, the empty space above its stack too, lights the column and prints "3.43 · 412 Openers" above its stack (`columnHeading`); the selected bar keeps its label. Counts are of the charted Openers, so under "Only Openers on the Answer List" they are the filtered counts. The label has a `--background` halo so it reads over blocks. Counts are not printed above every bar: at 14 units a bar is too narrow for four digits.

**Zoom into a bar.** Clicking or tapping a bar (a block or the empty space above its stack) selects it: it gets a `--heading` outline and a side column (`BarList`) opens, headed "3.43 · 412 Openers" with a close button. The column lists the bar's Openers in stack order, best first: word, rank, Average Guess Count (3 decimals), Losses and an Answer List swatch (the legend's colours, with screen-reader text). Highlighted words are on an `--accent` tint and bold. Clicking a word adds it to the highlight field (`addWord`). A long list scrolls inside the column (`max-h-72`, `26rem` on wide screens). From `lg` up the column sits right of the chart (`w-80`) and the chart frame narrows (and scrolls sideways inside itself); below `lg` it stacks under the chart, and the page never scrolls sideways. A single tap on a block does both jobs: it selects the bar and pins the tooltip. The selection is dropped when the Strategy changes and follows the Answer List filter (the list and count shrink). It stays on in the Article embed.

**Highlight tabs.** With `tabs`, a tab row (a shadcn `Tabs`, `components/ui/tabs.tsx`, Radix: a proper tablist with arrow-key navigation, aria-label "Highlighted words") sits above the cards, and shows even when `controls={false}`. The lists are in `lib/widgets/opener-presets.ts` (`OPENER_PRESETS`, each with `id`, `label`, `words`, `caption`); ranks are for `bits-guesses-all`: **Best Openers** (`best`: tarse #1, salet #3, crate #4, trace #5, slate #6, crane #7), **Myths** (`myths`: adieu, audio, ouija, soare, roate, raise), **Bad Openers** (`bad`: qajaq, xviii, zhuzh, jujus, jazzy, fuzzy) and **All** (`all`: the union, 18 words). Choosing a tab sets the `highlight` text to that list, so the URL's `highlight` param reflects the words; the caption of the current tab shows under the row (it is the tab panel). The current tab is not state: it is the preset whose words equal the highlight words (`presetFor`, order ignored), so typing in the highlight field to a list that matches none leaves no tab selected. With `tabs` on and an empty `highlight` prop the Widget starts on Best (the highlight default is the Best words); a `highlight` that matches no preset starts with no tab. `presetFor` and `unionWords` are tested in `opener-presets.test.ts`.

**Stat cards.** Each word in `highlight` is looked up by the pure `lookupOpener` (`lib/widgets/opener-lookup.ts`), and `sortLookups` orders the results: found words by rank, best first (not typing order), unknown words last. A word in the Strategy's Guess Pool gets a card above the chart (a responsive grid: one column on phones, two from `sm`, three from `xl`), in plain theme colours (no accent): the word in mono type on the left, with a `WordListBadge` ("Answer List" in accent, or "Guess List" quiet for a word only on the Guess List), and its rank ("#7", with a muted "of 14,855") on the right; the Average Guess Count (3 decimals) as the large number; and a muted line with the Losses (only when there are any) and "Bar 3.44 · 7 Openers" (the charted Openers in its bar, or "hidden: not on the Answer List"). Its block is drawn in the accent colour with its word printed, and the chart frame scrolls sideways to put the bar of the most recently added word in the middle (the frame only, not the page). With more than 6 found words (All has 18) the cards become a compact table, one dense row per word sorted by rank (word, its `WordListBadge`, #rank, Average Guess Count to 3 decimals, Bar and count), in the same plain colours, scrolling inside `max-h-64` with a sticky heading; the frame does not scroll to the newest word then, so the best end stays in view and the bad Openers on the right are reached by scrolling the chart. An unknown word gets a short "Not on the Guess List" note, or "Not on the Answer List" under an Answer List Strategy (when the summary is only partly built: "not on the Guess List, or not played yet").

**Phones.** A bar is at least 14 SVG units wide: the chart is a `min-width` box with the `<svg>` at `width="100%"`, inside an `overflow-x-auto` focusable region, so at 360px the chart scrolls sideways inside its frame and the page never does (checked: the document is exactly the viewport wide). The frame also scrolls on narrow desktops, since the bars alone are about 1,050 units wide.

**Pure functions** (`lib/widgets/opener-bars.ts`, `lib/widgets/opener-lookup.ts`, `lib/widgets/opener-column.ts`, tested with `bun test`): `barOf` rounds half-up on the exact integer Guess Count total (the average times 2,315, with the float error rounded away) as `floor((200 * total + 2315) / 4630)`, so no float error puts an Opener in the wrong bar; it is pinned in `opener-bars.test.ts` at the .xx5 edges (8160 and 8161 around 3.525). `barDomain` gives the first and last occupied bar and the tallest stack; `groupOpeners` keeps the empty bars between the first and last occupied bar (or over a given domain) and sorts each stack by `rank`; `sortLookups` orders the cards; `barColumn`, `columnHeading` and `addWord` build the side column's rows and heading and add a word to the field; `opener-presets.ts` gives the tab lists, `presetFor` and `unionWords`; `filterOpeners` is the Answer List filter (tested through the grouping); `labelRows` gives non-overlapping label rows; `lookupOpener` gives the found Opener, its bar and the size of its bar, or "incomplete" / "unknown".

The page `/openers` (`app/openers/page.tsx`, title "Opener Distribution") shows the Widget at the full width of `<main>`, with all controls, `tabs` and the Answer List toggle off (all 14,855 Openers), under a heading and a two-paragraph intro. The intro ends with a "How it works" link to Article 11. The sidebar's "Explore" heading links to the page.

### SplitGroups and the Opener Split page

`SplitGroups` (`components/widgets/SplitGroups.tsx`, memoised) draws a `POST /api/split` response with every word, as in the video's TRACE shot. Props: `split` (the response), `lang`, and the optional `highlightCode` (outlines that Feedback Code's block with the accent colour, `aria-current`) and `highlightWord` (draws that word as a strong, inverted tile) and `wordLink` (see "Follow this Answer" below; the Follow an Answer page does not pass it, so its words stay plain, non-focusable text). One block per Feedback (its head and words are the shared `SplitBlock`), biggest first, flowing left to right and wrapping (`flex-wrap`). A block's head is the Guess as five `Tile`s painted with that Feedback's Marks, with the word count under it (`pageText(lang).words`); the head Tiles shrink with the group (`headSize`: 100+ words full size, 25+ `small`, 5+ `board`, fewer `tiny`). Under the head, the words alphabetically in a grid of `columnCount(n, available)` columns (about the ceiling of √n, at least 1, capped at the columns that fit, measured with a `ResizeObserver` on the container, so a block is never wider than the space and the page never scrolls sideways). Words are plain tiles with no Mark colours: each is one `role="img"` element with five letter cells (not five `Tile`s), so the ~2,315 words of an Answer List stay light. The pure part is `lib/widgets/split-groups.ts` (`orderSplitGroups`, `columnCount`, `headSize`, `singleWordGroups`, `headStats`, and for Follow an Answer `statesPerRow`, `answerGroup` and `chainNodes`; `split-groups.test.ts`).

**Head stats card.** Every block head (given the Candidate Set size, `split.candidates`, so `SplitGroups` and the Answer's path nodes) is a hover target of one shared card per `SplitGroups` (`useHeadCard` in `HeadCard.tsx`, the Radix Popover of the word cards, anchored by `virtualRef` and looking like an `InfoTip`; `useHoverCard.tsx` is the shared hook behind it and the word cards, `z-[110]` above Full screen). The head carries its figures in `data-*` (`data-head` the Feedback Code, `data-guess`, `data-count`, `data-total`) and the card reads them, so it is one card, not a Popover per head. It shows the Feedback (the Marks as `tiny` Tiles), Words (the group size), Chance (`count/total` and `percent(count, total)`, as the explorer's chart formats it) and Information (`-log2(chance)` in bits, two decimals, from `headStats(count, total)`: `{ words, chance, bits }`, 0 bits for the whole set, `Infinity` for an empty group, tested in `split-groups.test.ts`). It opens on a mouse resting 150 ms on a head (closing 250 ms after it leaves), on a tap (a second tap closes it) and on keyboard focus, and Escape closes it. It is `pointer-events-none`, so it never gets in the way of a click, and a word card and the head card are never open together. The head is `w-fit`, so only the Tiles and the count are the target, and its accessible name includes the chance and the information. Keyboard: the heads of a split are one extra tab stop (roving `tabindex`, the last focused head or the first, kept apart from the words' tab stop, so a split is two tab stops, not hundreds): Left and Right (or Page Up and Page Down) move between heads, Home and End go to the first and last, Down goes to the block's first word (when the words are focusable) and Up from the first row of words comes back to the head. In Follow an Answer's Full split the heads work the same (the words there stay plain text).

The page `/opener-split` (and `/th/opener-split`) is `OpenerSplitView` (a Server Component taking `lang`, as `OpenersView` does) around `OpenerSplit`: a `WordRow` Opener input (URL param `opener`, default `salet`, via `useWidgetParam`) and `SplitGroups` of that Opener over the whole Answer List (`postSplit` with an empty State, 250 ms after typing stops). A word off the Guess List shows the API's message (`useGuessCheck`) and keeps the last good split on screen. All its text is in the page text table. On the `lg` breakpoint and up a "Full screen" toggle (`aria-pressed`, URL param `fit=1`, off by default, text in the page text table) opens fit mode, `FitView` in `OpenerSplit.tsx`: a full-window overlay (`fixed inset-0`, above the sidebar, body scroll locked) with a small bar (the Opener word and an X icon button named "Close", `closeFullScreen`; Escape also exits and clears `fit`) and the whole split scaled to fill the rest of the window inside a page margin (`px-6 py-4`, `sm:px-10 sm:py-6`; the area measured for the fit is inside the margin) with no scrolling, like the video's single shot. The split's height H(W) falls as its layout width W grows, and the best W is where H/W equals the window's height over its width; `FitView` finds it by bisection, each pass laying the blocks out at W (`SplitGroups` takes an optional `layoutWidth`, so column counts follow W, not the container; the layout effect re-runs before paint) and reading `scrollHeight`, then applies `transform: scale(min(width / W, height / H, 1))` from the top left, centred. It searches again when the window or the split changes, and on a window below `lg` the page shows the normal view.

**Bars view.** A "Blocks / Bars" `SegmentedControl` in the toolbar (a `Field` "View", "มุมมอง" in Thai, centred on the tiles like the other controls; URL param `view`, `blocks` the default and left out, or `bars`) swaps each Opener's `SplitGroups` for `SplitBars` (see the Feedback Split explorer: the title "Expected 71 words left · 5.83 bits", the scrollable bar list, one bar per Feedback, and the selected group's words beside it from `@2xl` of the column's own width, stacked below; the biggest group is selected to begin with). Its text comes from the page text table (`chartTitle`, `chartSummary`, `chartHint`, `chartLeft`, `chartChance`, ... in EN and TH), and its words are links with the "Follow this Answer" card, as in the Blocks view (each Opener's own `wordLink`). The stat card above each split stays. With Compare each Opener gets its own bars and list, in two columns from `xl` (each column's chart and list stacked, since a column is narrower than `@2xl`) and stacked below `xl`. The Full screen button is only shown in Blocks view (and `fit=1` is ignored in Bars view).

**Figures and Compare.** Above each split (`SplitFigures`) is a stat card: a rounded box (`rounded-md border-rule bg-highlight-low`, a container query box) whose header holds the Opener in the tile font (`font-tile`, uppercase, tracked) and a `WordListBadge` (`components/widgets/WordListBadge.tsx`: a quiet label (small text with a dotted underline, no box): the glossary term "Answer List" in accent for an Answer List word, "Guess List" muted for a word only on the Guess List, English in Thai too, drawn as a `TermTip` so it opens that term's glossary card on hover, focus or tap as `<Term>` does; the Opener is on the Answer List exactly when its split has an all-Correct group, `guessIsCandidate` in `lib/widgets/split-groups.ts`), then a `<dl>` of five equal cells with hairline dividers (each cell has a top and left border and the grid is shifted by -1px inside an `overflow-hidden` card, so dividers stay right however the cells wrap): two columns below 28rem of card width (the last cell spans both), five from there (`@md`, so each card is five across even when Compare puts two side by side). Each cell is a label (UI sans, `text-xs`, `text-meta`, a fixed two-line height so the values share a baseline) over a value (`text-lg`, tabular figures, one font; "bits" is a small `text-xs` suffix). The figures are Groups, Largest group and Expected Information and Expected Candidates (all from the split response: `groups`, `largest_group`, `bits`, `expected_candidates`), and Single-word groups, which `singleWordGroups` counts from the groups. They are formatted as the Feedback Split explorer's chart title is: `formatLeft` from `lib/widgets/split-chart.ts` for Expected Candidates (one decimal below 10, none from 10) and `toFixed(2)` plus "bits" for Expected Information. With Compare on, `betterFigures(split, other)` (pure, in `lib/widgets/split-groups.ts`, tested in `split-groups.test.ts`) says per figure whether this split is better (more groups, a smaller largest group, more single-word groups, more Expected Information, fewer Expected Candidates; `null` on a tie): the better value gets a small accent triangle in the cell's corner (`aria-hidden`, with an `sr-only` "better", the `betterFigure` page text) and the worse value is `text-meta`.

**Controls.** One toolbar row (`flex-wrap`, items aligned to the top): each field is an `eyebrow` label (a `Label` for the input, its own `h-6` row, so it never overlaps the tiles; the `WordRow` is rendered with `hideLabel`) over the tiles and the status line. The Compared Opener's Remove is a ghost `icon-sm` `Button` with an `X` (lucide) and `aria-label` "Remove", at the right of the tiles and centred on them; with Compare off a "+ Compare" `Button` (lucide `Plus`) takes the same place. "Full screen" is a `Button` with `Maximize2`, shown from `lg`, pushed to the right end (`ml-auto`). The action cells (`ACTION_CELL`) are as tall as the tiles and start below the label row, so the buttons share the tiles' vertical centre. All buttons are the default outline `Button` size (`h-9`). With Compare on, below `xl` the fields fill the row and Full screen wraps to its own row at the right.

The "Compare" button adds a second Opener (URL param `compare`, starting as `fuzzy`, the spec's bad Opener, so it sits under SALET) with its own input ("Compared Opener"), figures and `SplitGroups`; its "Remove" button takes it away and clears `compare`. Both inputs (`OpenerInput`: a stacked `Field` with the standard sentence-case label, the `WordRow`, the Remove button, the status line and its own error) sit side by side in the toolbar row at the top, above the splits, wrapping on a phone. Below the row each Opener's figures and `SplitGroups` are an `OpenerResult`: with Compare on they are two equal columns from the `xl` breakpoint (1280px; at `lg` the main column beside the sidebar is only about 780px, too narrow for two splits and five figures each) and stacked below it. Each `SplitGroups` measures its own column, so its word columns follow the column width. Compare stays on while the word is cleared to be retyped. Each Opener is an `OpenerPanel` driven by its own `useOpenerSplit` (the word's `useGuessCheck`, the debounced `postSplit`, the last good split), so a word off the Guess List or a failed split shows its message on its own input and leaves the other split alone. In Full screen with Compare on, `FitView` lays the two splits out side by side in two equal columns (a 48px gap, `FIT_GAP`) at the same layout width each (`(W - gap) / 2`, passed as `layoutWidth`), so the grid is 2W + gap wide and as tall as the taller column, and scales them together by one scale; the bisection runs on that total width unchanged. Its bar names both Openers (`SALET · FUZZY`) and the figures are not shown. 

**Follow this Answer.** The Opener Split page passes `wordLink={(answer) => followPath(lang, { answer, opener })}` with that split's own Opener (on Compare each split links with its own; no `pool`, `scope` or `by`, so the default Strategy), which turns every word into a `<button data-word>`. One shared card (a Radix Popover anchored by `virtualRef` to the active word, not a Popover per word) shows the word and a "Follow this Answer" link (`next/link`, `pageText(lang).followThisAnswer`, Thai links to `/th/follow`). It opens on a mouse resting 150 ms on a word (closing 250 ms after the pointer leaves the word and the card), on a click, on a tap (a second tap on the open word closes it) and on Enter or Space on a focused word, which also moves the focus to the link; Escape or a tap elsewhere closes it and, after a keyboard open, returns the focus to the word. The handlers are delegated on the `SplitGroups` root, and each block is a memoised `Block` that gets only its own picked/tab-stop word, so opening a card redraws one block, not 2,315 words. The picked word (the one whose card opened last) is drawn strong until another is picked; each split keeps its own pick, so on Compare the two are independent. Keyboard: the words of a split are one tab stop (roving `tabindex`: the last focused word, the first until then); Left and Right move along the words across blocks, Up and Down move by a row inside a block, Page Up and Page Down jump to the previous or next block, Home and End go to the first and last word. In Full screen the words are links too: the card is portalled to `<body>` above the overlay (`z-[110]`) and anchored to the scaled word's own rectangle, so the transform does not misplace it (the words are small at low scales).

### Follow an Answer page

`/follow` (and `/th/follow`) is `FollowView` (a Server Component taking `lang`) around `Follow` (`components/widgets/Follow.tsx`), which shows the Solver's Game for one Answer one row at a time. Inputs, all URL params through `useWidgetParam`: `answer` (a `WordRow`, default `watch`, the Answer of Article 08's Step-through Game), `pool`, `scope` and `by` (the shared `StrategyPicker`, given the page's `lang`), `opener` and `step` (the row shown, 1-based, default 1, clamped to the Game). The Answer and the Opener are `Field`s (inline layout, so their labels line up with the Strategy rows) around `WordRow`s with `hideLabel`; the "Full split / Answer's path" toggle is a `SegmentedControl`, and the controls sit in a `ControlPanel`. While it is untouched its param is empty and the box shows the Strategy's best Opener, which is simply Guess 1 of the `/api/solve` response made without `opener`, with a hint under it. Typing in the box sets `opener`, and a "Best Opener" button then clears it again. A typed Opener is sent as `opener` (`getSolve` takes it as its last argument) and needs all five letters. A word off the Answer List, or an Opener off the Guess Pool, shows the API's 400 message under its own input (the Opener's message starts with "opener").

The page calls `GET /api/solve` once (250 ms after typing stops) and then `POST /api/split` for the row shown (`Row`), with the State of the Guesses before it, caching each row's split in state so stepping back is instant. Row k is `SplitGroups` of Guess k over the Candidate Set before it, with `highlightCode` the Answer's group and `highlightWord` the Answer; its heading says the Guess number, the Guess and the size of the Candidate Set, and on the last row of a solved Game it says the Guess is the Win. The pure part, in `lib/widgets/split-groups.ts`, is `statesPerRow` (one State per row from a solve response) and `answerGroup` (the group of a split that holds a word), tested in `split-groups.test.ts` against responses recorded from the backend (`lib/widgets/fixtures/`).

**Answer's path view.** A "Full split / Answer's path" switch ("Split ทั้งหมด" / "เส้นทางของ Answer" in Thai) (a Radix `RadioGroup` in the strip, styled like the Strategy picker's rows) sets the URL param `view` (`split`, the default and left out of the URL, or `path`; an old `graph` counts as `path`). `/api/solve` carries only counts (`candidates_after`), not the Candidates, so the graph needs the Answer's group of every row: `useRowSplits` in `Follow.tsx` is the one per-row cache of `POST /api/split` responses (key: the Answer and the Guesses up to that row), shared by both views, and in path view asks for all missing rows in parallel. `FollowPath` (`components/widgets/FollowPath.tsx`) draws `chainNodes(solve, groups)` (`lib/widgets/split-groups.ts`) as an ordered list: an "Answer List · 2315 words" node on its own line, then a grid of three Guesses per row (one column below `sm`), each a plain arrow (→, ↓ on a phone) and a node as wide as its cell. A node is a small "Guess k" eyebrow (`pathGuess`) above a `SplitBlock` (`components/widgets/SplitBlock.tsx`, the head and words of one block, shared with `SplitGroups`) inside a button: the head is Guess k's Tiles painted with that Feedback's Marks (sized by `headSize`) with the word count under it, then the Answer's group as plain text in three columns, the Answer strong. A group over 40 words shows its first 40 alphabetically (the Answer always kept) and "+N more". The last node of a solved Game is the Win block: the Answer's Tiles all Correct, "Win" (`winLabel`, the glossary term, English in Thai too) in place of the count, holding just the Answer. A node is a button named "Guess 2: SALET, 12 Candidates left" ("Guess 4: CROOK, Win" for the Win block); clicking it sets `step` and returns to the full split. The head of a node opens the shared head stats card (see "Head stats card" above; `total` is the Candidate Set before that Guess, `candidates_before`) on mouse hover and on keyboard focus of the node's button (shown only for `:focus-visible`, the head itself not being focusable inside a button); it is `pointer-events-none` and the node opens it from hover and focus only, never from a click, so a click on a node always jumps to its step. The node of the current `step` is `aria-current="step"` and outlined. A node past Guess 6 has a thick `error` (red) border: in Wordle the Game is already a Loss there, even if that Guess wins.

The **Guess strip** (`GuessStrip`) is `position: sticky; top: 0` below the inputs, with a background and a rule, so it stays in view while the row scrolls (on a phone the top bar scrolls away, so the strip sits at the very top). It holds Prev and Next buttons (disabled at the ends), then each Guess as a button of `tiny` Tiles painted with its Feedback Marks, separated by chevrons, the current one marked (`aria-current="step"`, an outline), and "Guess k of n". Clicking a Guess, Prev and Next all set `step`; every control is a native button, so Tab and Enter work. The strip wraps on a phone and the page never scrolls sideways. The margin notes are not built yet.

### Charts

Charts use TanStack Charts: `@tanstack/react-charts` 1.1.0, which re-exports the `<Chart>` of its dependency `@tanstack/charts` (read `node_modules/@tanstack/charts/docs/` and `llms.txt`; it is not the old `react-charts` v3). A chart is a memoised `defineChart({ marks, scales, tooltip })` (marks such as `barY`, compact `scaleBand`/`scaleLinear` from `@tanstack/charts/scales/*`, the `tooltip` extension) passed to `<Chart definition height ariaLabel onSelect />`. `components/widgets/BenchmarkChart.tsx` is the only TanStack chart (it uses the shared `CHART_CLASS` wrapper from `ui.tsx`); the Feedback Split chart is plain elements (see its Widget section) because TanStack's axis labels cannot be coloured tiles.

- **Theme roles.** Mark paints are CSS variables (`fill: "var(--accent)"`, the selected bar `var(--heading)`), so a theme change repaints with no rebuild; the axes, grid and labels use `currentColor`, set by a `text-subtle` wrapper; the tooltip colours are set from `--overlay` and `--text` through the library's `--ts-chart-tooltip-*` variables. Charts never use fixed colours.
- **SSR.** `<Chart>` server-renders SVG at `initialWidth` and then measures its container after hydration. The Widgets only mount a chart once the API data has arrived on the client, so no chart markup is rendered on the server and there is nothing to mismatch; a definition must not read `window` or other client-only values if a future chart is rendered on the server.
- **Interaction.** The chart is keyboard focusable (arrow keys move between bars, Enter selects); the same selection is available from the list below, which also gives the exact values as text.

All Widgets show loading and error states (`role="alert"` for errors, `aria-live` for results), use real labelled inputs and buttons so they work from the keyboard, and wrap at phone width.
